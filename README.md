# 电商加购流失诊断（MySQL · Tableau）

用用户行为日志回答一个问题：**用户加购之后，为什么没有买？**

加购通常被视为强购买意向，但大量加购最终没有转化为购买。平台无法从日志中区分
「正在犹豫、还会回来」和「已经流失、需要召回」的用户，召回资源只能粗放投放。
本项目建设一条从原始日志到业务建议的完整链路：定义加购事件 → 配对转化结果 →
分层定位流失 → 量化召回窗口 → 输出干预建议。

## 研究问题

| 编号 | 问题 |
|---|---|
| RQ1 | 加购事件中最终完成同商品购买的比例是多少？与「浏览直达购买」相比如何？ |
| RQ2 | 加购流失在品类、商品热度、用户活跃度上如何分布？是否呈帕累托集中？ |
| RQ3 | 加购后转化时延如何分布？召回窗口是多少小时？ |
| RQ4 | 转化用户与流失用户在加购后的行为路径上有何可干预的差异？ |

完整的研究设计（假设、验证方案、局限）见 [`docs/00_研究设计.md`](docs/00_研究设计.md)。

## 核心方法

### 加购事件：本项目的分析单元

原始数据没有会话（session）标识。直接按行为行数统计「加购次数」，会把同一用户
连续刷新的多条记录当成多次独立意向。本项目先构造**加购事件**：

- 只取 `cart` 行为，同一 `(user_id, item_id)` 按时间排序；
- 相邻加购间隔 **超过 30 分钟**切分为新事件；
- 事件时间取该事件内首次加购时间。

30 分钟是设计选择而非数据事实，15 / 60 分钟阈值的敏感性检验同步进行。

### 转化定义

- **转化**：加购事件之后 7 天内，同一用户对同一商品出现 `buy` 记录；
- **窗口不重叠**：同一用户-商品多次加购时，一笔购买只归入最近的上一次事件；
- **右删失**：距数据终点不足 7 天的加购观察期不完整，事件级主指标剔除，
  同时保留对照，量化剔除前后的差异；
- **复购标记**：加购前已购买过该商品的，单独标记为复购型加购。

### 指标层级

事件级与用户级并列：前者回答「多少次加购完成了转化」，后者回答「多少人完成了转化」。
两种口径不可互相替代，报告中同时呈现。

## 数据

| 项目 | 说明 |
|---|---|
| 来源 | 阿里云天池公开的淘宝用户行为数据集（UserBehavior） |
| 时间范围 | 2017-11-25 至 2017-12-03 |
| 原始规模 | 约 9100 万行 |
| 分析底表 | 完整约 9100 万行（清洗后行数以实际执行结果为准） |
| 原始字段 | `user_id`、`item_id`、`category_id`、`behavior_type`、`timestamps` |
| 衍生字段 | `id`（自增主键）、`datetimes`、`dates`、`times`、`hours` |

全量数据下长尾商品的样本更充分，但窗口函数与自连接的计算代价显著上升，运行方案见下方「运行步骤」。
数据文件不入库（GitHub 单文件上限 100 MB），仓库只保存查询语句、文档与脚本。

**约定：一个 `.sql` 文件 = 一件独立的事。** 文件头写明功能、所属层、依赖表与状态，
方便单独执行、对比优化效果、在 GitHub 上看 diff。

全表直接调试代价高，`sql/00_数据准备/10_开发沙箱_临时表.sql` 会复制 10 万行到
`temp_behavior` 供秒级验证，分析文件按「小样本验证 → 全量执行」两段写。

## 运行步骤

1. **建表与导入**：`00_数据准备/01_建库建表.sql` → `02_导入数据.sql`
2. **清洗**：`04`–`09`，检查空值、重复、异常时间范围，补齐日期字段
3. **前置检查**：`11_前置检查.sql`，确认时间覆盖、行为分布与重复情况
4. **事件构造**：`10_dwd/01_加购事件构造.sql` → 产出 `dwd_cart_event`
5. **转化配对**：`10_dwd/02_加购转化配对.sql` → 产出 `dwd_cart_convert`

> 执行前把 Workbench 的 `DbSqlEditor:ReadTimeOut` 调到 **3600**，长查询才不会在第 600 秒断连。

## 已知局限

1. **无金额字段**：无法计算流失金额，RFM 缺少 M 维度，不做替代变量硬凑。
2. **无会话标识**：加购事件是近似口径，30 分钟阈值是设计选择。
3. **全量计算成本**：9100 万行的窗口函数与自连接需要联合索引、分批执行与较大内存，耗时随硬件差异明显；时间完整性与数据质量以前置检查结果为准。
4. **无曝光数据**：转化率分母是「发生过行为的用户」，不是曝光人群。
5. **`buy` 不等于支付成功**：可能存在下单未付。
6. **数据时效**：2017 年数据，结论不可直接外推到当前平台。

## 运行环境

| 项目 | 说明 |
|---|---|
| MySQL | 26.7 |
| 客户端 | MySQL Workbench 8.0 |
| 本机调试配置 | `innodb_buffer_pool_size = 4G`、`innodb_redo_log_capacity = 1G` |
| 全量执行建议 | 缓冲池 ≥ 16 GB，补 `(user_id, item_id, behavior_type, timestamps)` 联合索引；事件构造按 `user_id` 分批 |

**两条经验**：

1. 缓冲池不是越大越好。曾按「经验值」设为 8G，导致 MySQL 直接崩溃；
   后按机器实际可用内存降到 4G 才稳定。
2. 全表操作需要索引支撑。加购事件的窗口函数依赖 `(user_id, item_id)` 上的顺序扫描；
   转化配对若明显偏慢，补建 `(user_id, item_id, behavior_type, timestamps)` 联合索引。

## AI 使用说明

本项目在文档撰写与部分查询的整理过程中使用了 AI 编程助手，具体分工如下：

| 环节 | 参与方式 |
|---|---|
| 研究命题与假设 | 本人提出并定稿 |
| 指标口径（加购事件归并、转化窗口、右删失处理） | 本人决策，AI 协助整理为文档 |
| 新增查询（前置检查、事件构造、转化配对） | AI 起草初稿，本人在 MySQL 中执行、调试并通过自检 |
| 原有分析查询 | 保留自早期版本，作为指标资产 |
| README 与文档 | AI 协助起草与排版，本人核对事实与数据 |
| 结论与建议 | 全量数据执行后由本人根据结果撰写 |

所有可执行结论以实际查询结果为准。如发现表述或口径问题，欢迎指出。
