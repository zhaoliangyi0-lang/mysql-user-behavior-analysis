# 电商加购流失诊断 —— 研究设计

| 项目 | 内容 |
|---|---|
| 研究人 | 赵梁屹 |
| 版本 | v0.1（草稿） |
| 日期 | 2026-11-22 |
| 数据 | 淘宝用户行为日志（user_id / item_id / category_id / behavior_type / timestamps） |
| 分析底表 | `taobao.user_behavior` 全量 100,095,496 行（清洗后） |

> 本文档回答四个问题：**研究什么、为什么值得研究、指标怎么定义、结论怎么验证**。

## 一、背景与命题

### 命题

加购（cart）与收藏（fav）是电商平台最明确的购买意向信号，但大量加购最终没有转化为购买。
平台无法从日志中区分两类人：**正在犹豫的**（还会回来买）和**已经流失的**（不会再回来）。
两者对应的运营动作完全不同——前者该催付/给券，后者该召回——但现有粗放投放把两者混为一谈。

### 研究目标

用行为日志还原「加购之后发生了什么」，量化：

1. 加购后的转化率有多低、流失发生在哪一环；
2. 流失集中在哪些品类、商品热度带和用户群体；
3. 加购后多久内转化概率骤降（召回窗口）；
4. 转化者与流失者在后续行为上有何可干预的差异。

**明确不做的事**：不做金额分析（数据无价格字段）、不做归因建模（缺少对照组）、不构造无法验证的“预测模型”。

## 二、研究问题

| 编号 | 研究问题 | 对应分析 |
|---|---|---|
| RQ1 | 加购事件中最终完成同商品购买的比例是多少？与「浏览直达购买」路径相比如何？ | 漏斗、转化配对 |
| RQ2 | 加购流失在品类、商品热度、用户活跃度上如何分布？是否呈帕累托集中？ | 分层分析 |
| RQ3 | 加购后转化时延如何分布？召回窗口是多少小时？ | 转化时延曲线 |
| RQ4 | 转化用户与流失用户在加购后的行为路径（回访、再浏览、跨品类）上有何差异？ | 路径对比 |

## 三、待检验假设

假设必须可被本数据集证伪，证伪本身也是有效结论。

| 编号 | 假设 | 证伪条件 |
|---|---|---|
| H1 | 加购并不等于强购买意向：加购后同商品转化率显著低于「浏览后直接购买」的用户占比 | 加购转化率 ≥ 浏览直达购买率 |
| H2 | 流失高度集中在少数品类与长尾商品（前 20% 品类/商品贡献 ≥ 60% 的流失事件） | 流失分布接近均匀 |
| H3 | 加购后 24 小时内是转化黄金窗口，7 天后累积转化率增长趋近于零 | 7 天后的边际转化仍显著 |
| H4 | 转化用户在加购后 7 天内至少回访该商品一次的比例显著高于流失用户 | 两者回访率无显著差异 |

> H4 只用于**解释**流失，不用于预测：用“加购后的行为”解释“是否转化”存在同义反复风险，报告中须注明。

## 四、核心口径定义

### 4.1 为什么口径要自己定

数据集没有 session（会话）标识，也没有曝光日志。常见做法是直接按“行为次数”出指标，本研究会先定义**分析单元**，所有指标都统一到同一单元上，否则分子分母不可比。

### 4.2 加购事件（分析单元）

| 要素 | 定义 |
|---|---|
| 行为范围 | 主口径：仅 `cart`（加购）。`fav` 作为稳健性对照单独跑一遍 |
| 归并规则 | 同一 `(user_id, item_id)` 的加购记录按 `timestamps` 升序，相邻间隔 ≤ **30 分钟**归并为一次加购事件 |
| 事件时间 | 该事件内**首次**加购的时间 |
| 重复加购 | 间隔 > 30 分钟的再次加购计为新事件（视为重新产生兴趣） |
| 依据 | 30 分钟是通用 Web 会话超时标准；同时做 15 / 60 分钟敏感性检验 |

> 这一步是本项目的关键设计：“加购次数”只是原始行数，“加购事件”才是可解释的业务单元。

### 4.3 转化定义

| 要素 | 定义 |
|---|---|
| 转化条件 | 加购事件之后 **7 天内**，同一 `(user_id, item_id)` 出现 `buy` 记录 |
| 观察窗口 | 7 天（1 小时 / 1 天 / 3 天 / 7 天同时计算，用于曲线与敏感性） |
| 已购买过该商品 | 仍计为一次转化，但单独标记为“复购型加购” |
| 转化归属 | 同一 `(user_id, item_id)` 的多次加购，一笔购买**只归入最近的上一次加购事件**；事件窗口上界取「下一事件时间」与「加购后 7 天」的较早者，事件之间不重叠 |
| 右删失处理 | 数据集最后 7 天内发生的加购，观察期不完整，**事件级口径中剔除**，用户级口径中保留并注明 |
| 说明 | `buy` 是购买行为记录，不等于支付成功，报告中须声明 |

### 4.4 指标口径表

| 指标 | 定义 | 计算（纯文本） | 分母 |
|---|---|---|---|
| 加购事件数 | 归并后的加购事件总量 | COUNT(事件) | — |
| 加购用户数 | 至少有一次加购的去重用户 | COUNT(DISTINCT user_id) | — |
| 加购转化率（事件级） | 主指标 | 转化事件数 / 加购事件数 | 加购事件 |
| 加购转化率（用户级） | 对照口径 | 7 天内买过所加购商品的用户 / 加购用户 | 加购用户 |
| 转化时延 | 加购到同商品购买的小时数 | buy 时间 - 加购事件时间 | — |
| 累积转化率（t） | 加购后 t 小时内已转化比例 | 时延 ≤ t 的事件数 / 加购事件数 | 加购事件 |
| 流失集中度 | 前 20% 主体贡献的流失占比 | 累计流失事件 / 总流失事件 | 流失事件 |
| 加购后回访率 | 加购后再次浏览同商品的用户占比 | 回访用户 / 加购用户 | 加购用户 |

> 事件级与用户级必须并列呈现：同一用户多次加购会被事件级重复计数，用户级则被一次购买“洗白”，两者回答的问题不同。

### 4.5 分层维度

| 维度 | 定义 |
|---|---|
| 品类 | `category_id`，长尾品类合并为“其他” |
| 商品热度 | 加购事件前该商品全期交互人数，按四分位分 Q1–Q4 |
| 用户活跃度 | 加购事件前 7 天内该用户的行为条数，按四分位分 Q1–Q4 |
| 加购时段 | 加购事件所在小时 |
| 行为路径 | 沿用现有 4 位码（浏览/收藏/加购/购买） |
| 用户价值 | 沿用现有 RF 分层（无 M 维度） |

## 六、验证方案（本项目的方法论核心）

| 检验 | 做法 | 通过标准 |
|---|---|---|
| 会话窗口敏感性 | 15 / 30 / 60 分钟分别构造事件，比较核心转化率 | 三档结论方向一致，差异 < 3 个百分点 |
| 转化窗口敏感性 | 1h / 1d / 3d / 7d 累积转化率 | 结论不随窗口选择反转 |
| 口径对照 | 事件级 vs 用户级 | 差异可解释，不隐藏任一结果 |
| 右删失检验 | 剔除最后 7 天 vs 不剔除 | 主结论不变 |
| 分时段稳健性 | 按日期切分，比较各时段核心指标 | 各时段结论方向一致 |
| 数据完整性 | 检查全量数据的时间覆盖、断点与重复 | 覆盖完整；若有缺口，注明受影响的分析 |

> 任何一项不通过，都在报告中如实写明，并说明结论的适用范围。**不做选择性报告。**

## 七、已知局限

1. **无金额字段**：无法计算流失金额，RFM 缺少 M 维度，只能用次数替代，须注明。
2. **无 session 标识**：加购事件为近似口径，30 分钟阈值是设计选择而非数据事实。
3. **全量计算成本**：1 亿行的窗口函数与自连接对内存、索引和临时表空间要求高，执行时间可能以小时计；不同硬件下的复现耗时差异明显。
4. **无曝光数据**：无法计算真正的转化率分母（曝光→购买），只能用“行为发生者”作分母。
5. **`buy` 不等于支付成功**：可能存在下单未付。
6. **数据集时效**：2017 年数据，结论不可直接外推到当前平台。

## 八、方法与口径来源

- **数据**：阿里云天池公开的淘宝用户行为数据集（UserBehavior），全量约 1 亿行。
- **分析框架**：按“人 / 货 / 平台”整理的指标资产作为素材库，按研究问题调用，不作为目录结构。
- **核心口径**：加购事件、转化窗口、右删失处理、事件间不重叠等，均由本研究根据数据条件定义，并在第四节与第十节记录。
- **不适用的指标**：无法验证口径的指标降级到附录或删除，避免用近似指标冒充精确结论。

## 十、口径决议（2026-11-22 确认）

| 决策点 | 决定 | 理由 |
|---|---|---|
| 意向行为范围 | 主口径**只用 `cart`**；`fav` 单独跑作对照 | 收藏的购买意愿弱于加购，合并会稀释转化率、模糊结论 |
| 转化窗口 | 主口径 **7 天**，同时计算 1h / 1d / 3d / 7d 累积曲线 | 7 天覆盖多数复购周期；召回窗口从曲线上读出，而非预设 |
| 主指标层级 | **事件级与用户级并列** | 两者回答“多少次加购转化”与“多少人转化”，口径不同不可互相替代 |
| 右删失 | 事件级**剔除**观察期不完整的末段加购，另做不剔除对照 | 避免系统性低估转化率；对照结果写入报告 |

> 以上为项目主口径。任何在分析过程中变更的口径，须在本文档记录变更原因与影响。
